# AsylumEnforce / phese(폐쇄!) 위협 모델

AsylumEnforce(한국어 별칭: **어떻게 병동이름이 폐쇄야 보호 시스템**)의 PHP 보호 계층은 **phese — PHP high enforcing-security essentials, 폐쇄!**이다. 이 프로젝트의 목표는 취약한 PHP 런타임의 실행을 거부하고, 허용된 PHP 프로그램의 운영체제 권한과 접근 범위를 줄이는 것이다. 모든 CVE 방어 또는 모든 기존 프로그램의 무변경 호환성을 보장하지 않는다.

이 문서는 설계상 보호 경계와 한계를 설명한다. 서버에 실제 적용된 구성, 빌드와 검증 결과는 배포 기록으로 별도 확인해야 한다. 저장소에 정책 파일이 있다는 이유만으로 실행 중인 PHP-FPM이나 컨테이너가 보호되는 것은 아니다.

## 보호 대상과 공격자

보호 자산은 호스트의 관리자 권한, 비공개 파일, 다른 서비스의 데이터, 애플리케이션 코드의 무결성 및 서비스 가용성이다. 공격자는 HTTP 요청·업로드·직렬화 데이터 등 애플리케이션 입력을 조작할 수 있다고 가정한다. PHP 코드 실행이나 PHP 엔진의 메모리 손상으로 worker 권한을 얻는 상황까지 고려한다.

호스트 관리자, 커널, bubblewrap 실행 파일, PHP 바이너리, 로드한 네이티브 확장, phese 정책 및 배포 경로는 신뢰 영역이다. 이 중 하나가 이미 변조됐거나 공격자가 호스트 root 권한을 가졌다면 이 시스템의 보호 범위를 벗어난다. 호스트 root로 PHP 애플리케이션을 실행하지 않아야 한다.

## 계층별 경계

| 계층 | 역할 | 한계 |
| --- | --- | --- |
| PHP 버전 검사 | 지정한 두 CVE가 수정된 릴리스를 실행 전 확인하고 미지원·취약 버전을 거부 | 버전 문자열만으로 바이너리의 진위나 모든 후속 취약점을 증명하지 못함 |
| 네이티브 확장과 seccomp | 정책이 금지한 커널 작업을 PHP 프로세스에서 제한 | PHP 엔진 버그를 고치는 패치가 아니며, 허용 syscall과 파일·소켓에 대한 공격은 남음 |
| standalone bubblewrap sandbox | 애플리케이션 읽기 전용 mount, 명시한 쓰기 경로 및 기본 네트워크 차단으로 실행 환경 제한 | 커널 취약점, 허용 경로 내부 손상, 자원 고갈 및 명시적으로 허용한 통신까지 제거하지 못함 |
| 소스 검사와 수정 요청 | 호환성·보안 검토가 필요한 코드를 찾아 로컬 검토 자료 생성 | 정적 패턴 검사는 오탐·미탐이 있으며 프로그램의 안전성 증명이 아님 |

standalone 실행은 namespace 또는 필수 보호 구성에 실패하면 중단해야 한다. bubblewrap이 없거나 실패했을 때 일반 PHP 실행으로 자동 후퇴하면 안 된다. 애플리케이션은 기본 읽기 전용이며 `--write`로 명시한 경로만 쓰기를 허용한다. 데이터베이스·캐시·업로드처럼 쓰기가 필요한 디렉터리는 각각 별도로 지정하고 범위를 최소화해야 한다. 앱 전체나 호스트 전체를 쓰기 허용하면 무결성 경계가 크게 약해진다.

네트워크는 기본 차단한다. `--network host`에서는 정상 API 호출과 함께 SSRF·외부 유출 가능성이 다시 생긴다. 애플리케이션이 기존 소켓·파일 descriptor·비밀 환경변수를 물려받지 않도록 launcher와 배포 정책도 검토해야 한다. 샌드박스가 애플리케이션에 제공한 비밀 값은 해당 애플리케이션의 PHP 코드나 네이티브 RCE로부터 비밀이 아니다.

## 호환성과 수정 요청

동작을 무조건 유지하면서 임의의 위험한 동작만 완벽하게 판별하는 것은 불가능하다. 프로세스 생성, 외부 명령, 특정 확장, JIT·실행 가능 메모리, 네트워크, 동적 코드 평가, 앱 디렉터리 쓰기 같은 동작은 정책과 충돌할 수 있다. PHP `eval()`을 전면 금지하는 정책은 이를 사용하는 템플릿·생성 코드 등의 호환성을 깨뜨릴 수 있다. `eval()` 허용 여부와 syscall containment는 다른 문제이다.

애플리케이션의 PHP 코드는 자동으로 재작성하지 않는다. 검사 결과는 **수정 요청**으로 로컬 파일에 남기고 사람이 검토한다. 로컬 수정 요청 생성은 개발자에게 외부 메시지를 발송하거나 GitHub Issue를 등록한 것과 다르다. 운영 로그에서 발견한 오류 또한 비밀 값과 요청 본문을 제거한 후 검토해야 한다.

## 남는 위험

- SQL injection, XSS, 인증·인가 오류, 비즈니스 로직 오류는 이 계층만으로 차단되지 않는다.
- `--network host`의 SSRF·유출과 허용 데이터베이스 계정의 오용은 별도 통제가 필요하다.
- 허용한 파일의 읽기·쓰기, 데이터 파괴 및 PHP 프로세스가 이미 가진 비밀의 유출은 발생할 수 있다.
- seccomp·namespace는 커널 취약점에 대한 보장이 아니다. 호스트와 관련 패키지의 보안 업데이트가 계속 필요하다.
- CPU·메모리·디스크·프로세스 자원 고갈은 별도 제한과 모니터링으로 다룬다. 미패치 PHP에 `RLIMIT_AS`·`RLIMIT_DATA`를 추가하는 것은 아래 OOM 취약점의 대책이 아니다.
